# White Paper Generation Pipeline

*Documented 2026-10-01*

## Overview

The white paper is generated by `white_paper_writer.py`, a dependency-aware
iterative drafting loop that calls **gpt-5.6-sol** (Azure OpenAI) to write,
review, and revise each section of the paper. It produces two output files:

| File | Description |
|---|---|
| `white_paper_draft.md` | Final assembled paper in Markdown |
| `white_paper_log.json` | Full iteration log: all drafts, grades, and feedback per section |

The QMD source (`white_paper.qmd`) mirrors `white_paper_draft.md` with a
Quarto YAML header added, and is used to render the deployed HTML.

## Section Dependency Structure

Sections are written in **three passes** to ensure that each section has
finalized upstream context injected into its writing and review prompts.

```
Pass 1 — Independent body sections (run in sequence)
  S2 → S3 → S4 → S5

Pass 2 — Depend on Pass 1
  S6 (Discussion)   ← depends on S3, S4
  S7 (Conclusion)   ← depends on S3, S4, S5, S6

Pass 3 — Written last, after all other sections are finalized
  S1 (Introduction) ← depends on S2, S3, S4, S5, S6, S7
```

Full dependency map:

| Section | Depends on |
|---|---|
| S1 Introduction | S2, S3, S4, S5, S6, S7 (all) |
| S2 Supply Chain Structure | — (none) |
| S3 Simulation Framework | S2 |
| S4 Sensitivity Analysis | S2, S3 |
| S5 SKILL Approach | S2, S3, S4 |
| S6 Discussion | S3, S4 |
| S7 Conclusion | S3, S4, S5, S6 |

**Execution order:** S2 → S3 → S4 → S5 → S6 → S7 → S1

**Assembly (reading) order:** S1 → S2 → S3 → S4 → S5 → S6 → S7

### Implication for targeted re-runs

Because upstream context is injected into downstream prompts, changes to an
early section can affect the consistency of later sections. The table below
guides how far downstream a re-run must go when a section is revised:

| Section revised | Minimum re-run scope |
|---|---|
| S2 | S2 → S3 → S4 → S5 → S6 → S7 → S1 (full re-run) |
| S3 | S3 → S4 → S5 → S6 → S7 → S1 |
| S4 | S4 → S5 → S6 → S7 → S1 |
| S5 | S5 → S7 → S1 |
| S6 | S6 → S7 → S1 |
| S7 | S7 → S1 |
| S1 only | S1 only |

For **minor additions** (a paragraph or short passage added to S2 that does
not change existing content), it is acceptable to re-run S2 alone and then
re-run S1 to update the introduction framing, skipping S3–S7 if their
content is unaffected.

## Per-Section Write–Review–Revise Loop

For each section, the pipeline runs the following loop:

```
1. Write initial draft
     Input:  PAPER_CONTEXT + upstream finalized sections + section brief
     Output: initial draft text

2. Review
     Input:  initial draft + PAPER_CONTEXT + upstream context + section brief
     Output: JSON with grades (clarity, accuracy, audience_fit, overall)
             + feedback bullet points + revised_draft

3. If all grades ≥ 8 (PASS_THRESHOLD) → accept
   Else → use revised_draft as new draft, repeat from step 2

4. Maximum 3 iterations (MAX_ITER). If still below threshold after 3
   iterations, accept best available draft with a warning.
```

### Grading rubric

| Dimension | Measures |
|---|---|
| `clarity` | Jargon-free, easy to follow sentence by sentence |
| `accuracy` | Facts, numbers, and logic correct and internally consistent |
| `audience_fit` | Tone and depth appropriate for non-technical clinical operations readers |
| `overall` | Holistic quality |

Pass threshold: **8/10** on all four dimensions.

## Running the Full Pipeline

```bash
cd "White Paper"
python3 white_paper_writer.py
```

Runtime: approximately 10–20 minutes for a full 7-section run (7 sections ×
up to 3 iterations × 2 API calls per iteration).

---

## Running a Targeted Re-run (Gap Fixes)

To revise specific sections without re-running the entire paper, modify
`white_paper_writer.py` as follows:

1. Update the `brief` for any section(s) that need new content (e.g., add
   IRT, sustainability framing, manufacturing context to S2's brief).
2. Set `EXECUTION_ORDER` to only the sections that need to be re-run,
   following the minimum re-run scope table above.
3. Pre-populate `finalized` with the existing final drafts for any sections
   that are *not* being re-run, so they still appear in upstream context.
4. Run the script. The outputs overwrite `white_paper_draft.md` and
   append to `white_paper_log.json`.

After a targeted re-run, re-render and redeploy:

```bash
quarto render white_paper.qmd
# then deploy via rconnect-qa API (see infra.md)
```
